L02 Distributed Data Processing

Exam questions

Your dataset is 3 GB and fits in memory. Why not use Spark anyway?

Key points: essential versus accidental complexity; Spark adds a cluster, scheduling, lazy plans and new failure modes; pandas or Polars handle the case; scale only when data size and latency demand it.

The solution should only be as complex as the problem. A 3 GB dataset that fits in memory is small data: pandas handles complex operations on it and Polars can use every core of the machine for simple ones. Spark would add accidental complexity: a session and cluster to configure, lazy plans to debug, partitions and shuffles to tune, and more things that can fail, while solving nothing pandas cannot. The course’s rule is to avoid concurrency, distributed computing and GPU computing as long as you can, and move along the line from single core to multiprocessing to distributed computing only when data size and latency requirements push you there.

How would you compute the mean of a dataset spread across several machines, and why not average the machines' means?

Key points: split the data into chunks; each worker computes a local sum and count; the coordinator divides the total sum by the total count; averaging means is only correct for equal-size chunks; only two numbers per worker cross the network.

Split the data into chunks and give each worker one. Each worker computes the sum Sk​ and count nk​ of its chunk and sends only those two numbers back. The coordinator computes ∑k​Sk​/∑k​nk​. Averaging the workers’ means gives the right answer only when every chunk has the same size: with chunks [1, 2, 3] and [10] the means are 2 and 10, their average is 6, but the true mean is 4. Sending sums and counts is also cheap, because the raw data never moves. In Spark terms, this is why a global average is cheap: partial results are computed locally per partition and only those are combined.

Why does your pipeline store its data as partitioned Parquet instead of CSV?

Key points: columnar layout reads only needed columns; per-column encoding compresses well; footer metadata and statistics let readers skip row groups; partition folders let readers skip whole days; types and schema are stored.

Analytical and ML jobs read a few columns of many rows, the OLAP pattern. CSV is a row format: to use one column you parse every byte of every row, and nothing says what type a field is. Parquet stores each column of a row group as a separate chunk, so a reader fetches only the columns it uses. Values of one column are similar, so they encode and compress well, which cuts disk and network traffic. The footer holds the schema, the location of each column chunk and statistics such as minimum and maximum values, so a filter can skip row groups that cannot match. Partitioning the folder by day (chck_date_day=...) lets a reader skip whole days, which also makes reading only new data cheap.

What is the difference between OLTP and OLAP, and why should an ML training job not query the app's backend database directly?

Key points: OLTP serves the backend: few records by key, low-latency writes, wide results; OLAP serves analytics: aggregates over many records, bulk loads, tall results; backend stores are optimised for OLTP; big queries cause latency spikes for users.

OLTP (online transaction processing) is the backend’s workload: fetch or update a few records by key, such as one user’s profile, with low-latency writes from user input, returning wide results (many columns, few rows). OLAP (online analytics processing) is the analytics workload: aggregate over huge numbers of records, loaded in bulk by ETL, returning tall results (many rows, few columns), on TBs to PBs of data. A backend database is laid out and tuned for OLTP, typically row-wise. A training job’s full-history scan is slow there and competes with the app’s own queries, causing latency spikes for real users, whose requests take priority. So the data is copied out to storage built for analytics, such as Parquet files, and the heavy reads happen there.

Which of your Spark operations are narrow and which are wide, and why does it matter?

Key points: narrow: each output partition needs one input partition, no data movement (arithmetic, filter, sample); wide: needs rows from many partitions (groupBy, join, sort); wide triggers a shuffle through disk and network; shuffles dominate cost; global count/avg only move partial results.

In a narrow operation every partition can be processed on its own executor without seeing other data: column arithmetic like the z-score withColumn, filters, sampling. In a wide operation an output depends on rows spread over many partitions: a groupBy needs all data for one key together (Spark first reduces each partition to partial aggregates per key), a join needs matching keys together, a sort needs global order. Spark meets that with a shuffle: rows are written out, sent over the network to the executor that owns their key, and read back. That is usually the most expensive part of a job, so you filter and select before grouping or joining, to shuffle less data. A join with a small table, such as per-group statistics, avoids shuffling the large side, because Spark broadcasts the small table to every executor. A whole-dataset count or average is cheap despite combining all partitions, because each partition sends only its partial count or sum.

When does Spark actually execute your code, and what does it gain from waiting?

Key points: transformations only build a plan; actions (head, collect, count, show, write) trigger execution; seeing the whole plan lets Spark optimise; filter reordering, column pruning and predicate pushdown into Parquet; explain() shows the plan.

Spark is lazy. Transformations such as select, filter, withColumn and join return immediately and only add steps to a plan. Execution starts when an action needs a result: head, collect, count, show or write. Because Spark sees the whole plan first, it can optimise it. In the demo the code doubled amount and then filtered on it, but the physical plan filtered first, read only the amount column from Parquet (column pruning), and pushed the amount > 100 condition into the Parquet scan (predicate pushdown), where row group statistics can skip data. explain("formatted") shows that plan without running anything. A practical consequence: a runtime error surfaces only at the action, so the line that fails is not always the line with the bug, although a misspelt column name is caught at once.

Key points: local[2] means everything on one machine with two cores; at most two tasks run at once, the rest queue; roughly one task per partition; driver plans and schedules, executors run tasks; a cluster adds executors on worker nodes via the cluster manager.

local[2] runs everything on your own machine with two cores, so at most two tasks run in parallel and the other tasks wait in a queue. Spark creates roughly one task per partition, plus tasks for work such as listing files and reading the schema. On a cluster, the driver still builds the plan and splits it into tasks, but a cluster manager gives it executors on several worker nodes, each running several tasks in parallel and caching data, and exchanging data with each other in shuffles. More executor cores means more tasks at once; more tasks than cores just means tasks queue. Very many tiny partitions waste time on scheduling, which is why Spark packs small files together when reading.

Your daily scoring job did not run for four days. How does your design recover without code changes?

Key points: do not hard-code “process yesterday”; read the delta between source and sink; keep state of the latest processed timestamp; independent of the scheduler; cold start and backfills handled; cost is a long catch-up run.

A job that reads only the previous day would need code changes and manual runs for each missing day. Replaying the scheduler’s missed triggers works most of the time, but it cannot handle a cold start (data from before the first release, for which no trigger exists) and makes migrations painful. My job instead reads the delta: everything in the source that has no result in the sink yet, found using a saved state with the latest processed timestamp. Whenever it starts, it processes what is missing: one day normally, five days after the outage, all history on the first run. The trade-off is that a catch-up run can take a long time. Because a second run finds an empty delta, the job is also idempotent: rerunning it does not duplicate predictions.

Your job ran for two days and then crashed on a bug. How would you design it so you do not lose two days?

Key points: a single long task is all-or-nothing; use checkpoints that store each operation’s result; or split into tasks that save and read intermediate results; rerun only the failed part; intermediate storage must be shared and durable, not the local disk; costs complexity.

As a single task with no intermediate data, the job either completely succeeds or completely fails, which is fine for short pipelines and painful for long ones. Two fixes: checkpoints, where each operation’s result is stored automatically and a replay resumes from the last one; or splitting the pipeline into tasks (preprocessing, features, prediction) that each write their output to intermediate storage and read their input from the previous task’s output, so only the failed task reruns. The intermediate storage must not be the local hard disk: the crashed machine may be gone and other workers cannot read it. The price is storage and a more complex design. Spark itself recomputes lost partitions when an executor dies, but that does not survive the application crashing.

The run was green but half the predictions are missing from the sink. How did that happen and how do you prevent it?

Key points: connection broke mid-write; a fire-and-forget write never learns of the failure; use an ACID sink so a broken write rolls back; mark success only on ACK, retry on NACK; latency cost is acceptable for batch.

The processing succeeded but the connection broke during the write. With a connectionless, fire-and-forget method, the writer never learns which writes failed, so the run reports success. Two fixes: write to a database with ACID properties, so a transaction either commits completely or is rolled back (atomicity) and a committed one survives failures (durability); and make the run’s success depend on acknowledgements, so a NACK or missing ACK triggers a retry or fails the run. Then a green run means the results reached the target. Waiting for acknowledgements adds latency, which a batch job can afford.

L03 Containerization and Software Engineering Processes

Exam questions

The same one-line Python script runs on your colleague's laptop and fails on yours. Why can that happen, and how do containers fix it?

Key points: machines differ in architecture, OS, OS configuration and package versions; example: print with flush exists only from Python 3.3, a syntax error in 2.7; a container packages code with its interpreter and dependencies; it runs isolated on any host the same way; pin image versions.

Machines differ at several levels: CPU architecture, operating system and version, how the OS is configured, and which packages and versions are installed. Each can change how code runs. Even print('hello', flush=True) works on Python 3.3 and later and is a syntax error on Python 2.7, because flush did not exist; and NumPy once gave different float32 results on Intel and Apple M1 machines with identical package versions. A container packages the application together with its interpreter, libraries and configuration into an image, and runs it as an isolated process on any host with a container engine, so every machine runs the same software stack. The image tag should be pinned, since a floating tag like python:3-slim changes over time, and the image’s CPU architecture should match the server’s.

What is the difference between a virtual machine and a container, and why has containerization replaced VMs for deploying applications?

Key points: VM packs a whole computer, with its own guest OS on a hypervisor; container shares the host OS kernel and packs only the app and its dependencies; containers are lighter, start faster, waste fewer resources; one container per application instance; shipped as images via a registry to an orchestrator.

A virtual machine emulates a whole computer on a hypervisor, and each VM brings its own operating system. That makes VMs heavy: every application carries a full OS, which wastes memory and disk, and VMs are slow to start and awkward to manage. A container runs on the host’s existing operating system and packages only the application and its dependencies, isolated from the host and from other containers. Many containers share one OS, so they use far fewer resources and start in seconds. The deployment flow becomes simple: build the image, push it to a registry, and let an orchestrator run it; the same image runs the same way everywhere. One container is one application instance, which keeps systems neat. The trade-off is weaker isolation than a VM, because containers share the host kernel.

Your Docker image takes ten minutes to rebuild after every one-line code change. Why, and how do you fix it?

Key points: each Dockerfile instruction is a cached layer; a change invalidates that layer and all later ones; copying all code before installing dependencies reinstalls packages on every change; copy requirements.txt and install first, then copy code; .dockerignore keeps the context small.

An image is built in layers, one per instruction, and Docker caches each layer. When an instruction or the files it copies change, that layer and every layer after it are rebuilt. If the Dockerfile copies the whole project before pip install, any code edit changes the copy layer, so all dependencies are reinstalled. The fix is to copy only requirements.txt first, install the dependencies, and copy the source code afterwards: code edits then only rebuild the last, cheap layers, and dependencies are reinstalled only when requirements.txt changes. A .dockerignore that excludes data, virtual environments and .git also keeps the build context small and stops large files ending up in the image.

Your unit tests mock the database and all pass. Why do you still need integration tests, and why are there fewer of them than unit tests?

Key points: a mock returns what you tell it, so wrong SQL, column names or types pass; integration tests check interaction with real systems; pyramid: many unit, fewer integration, few E2E; higher up is harder to implement and harder to find root causes; all automated.

A unit test mocks external dependencies so it can check your own logic fast and in isolation. But the mock returns whatever rows you tell it to, so it cannot tell you whether your SQL is correct: a typo, a wrong column name or a type mismatch with the real table passes every unit test. Integration tests run your code against the real system, such as an actual database, and check that the interaction works. In the testing pyramid, unit tests form the wide base, integration tests the middle and end-to-end tests, which simulate the user, the top. Moving up, tests are harder to implement, and a failure is harder to trace to its root cause, so you write many unit tests and fewer integration and end-to-end tests. All levels must be automated.

How would you automate an integration test of your data loading code against a PostgreSQL database?

Key points: FIRST requires isolation, so no shared dev database; run Postgres in its own container from an existing image; Docker Compose starts DB and test containers together; connect via service name, wait for a health check; create known data in setup, tear down volumes; exit code from tests for CI.

Tests must be isolated and repeatable, and a shared development database is neither: others change its data and the test machine may not even reach it. So the database runs in its own container, from an existing PostgreSQL image, set up exactly as the test expects. A Docker Compose file defines two services, the database and a container built from the project’s Dockerfile, with the repository mounted so the tests are inside, that runs pytest tests/integration. The tests connect to the database by its service name (db:5432), since localhost inside a container is the container itself. The test service depends on the database with a health check condition, because a started database is not yet ready for connections. A fixture creates a table with known rows, the test calls the real query function and compares the result, and docker compose down -v removes the data so every run starts clean. Running compose with --exit-code-from tests makes the test result the command’s exit code, so CI can run it automatically.

An intern sends "Integration Test Email #1" to all subscribers. Whose fault is it, and which processes would have prevented it?

Key points: the engineering processes’ fault; mistakes happen, they must not happen in live environments; layered Dev, Acc, Prod with the same tech stack; Acc is a production replica at low scale with no production data; production protected, changes only via reviewed PRs and CD.

The fault lies with the engineering processes. Mistakes are inevitable; the process has to ensure they cannot happen in the live environment. Layered environments do that. Developers work locally and in a development environment, a free-for-all sandbox with access to their own systems only. The acceptance environment is a replica of production with the same tech stack and all systems integrated, so the whole product can be tested there, but at low scale and with no production data, so a test email sent there has no real subscribers to reach. Production is live and protected: nobody pushes changes to it by hand. With GitFlow, changes reach it only through an approved pull request into main, which triggers continuous deployment.

How does GitFlow connect branches to environments, and how is an urgent production bug fixed?

Key points: main points to Prod, develop to Acc; features branch from develop and merge back via PR; merges are protected and trigger CD to the target environment; release branches go from develop to main with a version tag; hotfix branches from main, merged into main and develop.

GitFlow has two long-living branches: main, whose state is the state of production, and develop, whose state is the state of acceptance. New features, refactoring and bug fixes are built on feature branches from develop and merged back into it through pull requests. Merging into main or develop is protected and triggers continuous deployment to the matching environment, so develop is always what acceptance runs and main what users get. A release branch is cut from develop, stabilised, and merged into main with a version tag and back into develop. An urgent production bug gets a hotfix branch from main, the only branch that starts there; once fixed it is merged into main (a new version, deployed to production) and into develop, so the fix is not lost in the next release.

What is a pull request for, and what can go wrong with code review?

Key points: a request to merge changes, opened for review; must be approved before merge; author and reviewers share responsibility; anyone can review regardless of seniority; raises quality and spreads knowledge; ego: aggressive reviewers, authors taking comments personally; keep PRs small and focused.

A pull request asks the team to merge a set of changes into a protected branch and opens those changes for review. Team members review and approve or reject; without approval the PR cannot be merged. Author and reviewers then share responsibility for what is merged, and seniority does not matter: anyone can review. Reviews increase quality, since another person catches what the author missed, and team members learn from each other’s code. The risk is ego: a reviewer may approach the review aggressively, and an author may take comments personally. Good PRs make review easier: small and focused on one problem, split into logical commits, with tests and a concise, complete description written by the author.

Your project needs to ship by Friday and you are tempted to hard-code paths and skip the integration tests. How should you treat that decision?

Key points: that is technical debt: future cost of a quick solution now; avoid the loan if you can; if taken, make it explicit and record it; do not go too deep; ideally deliberate and prudent, tracked and repaid.

Hard-coding paths and skipping tests is technical debt: an easy, quick solution now that incurs a future cost compared with the better, slower approach. Every later change to that code becomes slower and riskier. The lecture’s rules follow the loan analogy: do not take the loan if you do not have to; if you must, make it explicit and record it, for example as an issue or a note in the README saying what was skipped and why; and do not go too much into debt, because accumulated shortcuts make every new change expensive. In Fowler’s terms the aim is deliberate and prudent debt, tracked and repaid once the deadline has passed.

What would you use MLflow for in an ML project, and when would you not bother?

Key points: experiment tracking (parameters, metrics, artifacts per run); model registry and management; model serving; log model as pickle, artifacts, metrics such as F1; optional for most projects; the tracking server is another external dependency.

MLflow tracks experiments: each training run records its parameters, metrics such as the mean and standard deviation of the cross-validated F1 score, and artifacts such as a JSON file of fold scores and the pickled model, so runs can be compared and the best one reproduced. It also offers a model registry to version and manage trained models, and model serving. It is popular but, in Yesilbek’s words, definitely optional for more than 90% of projects. When used, the MLflow tracking server is one more external system the application depends on: it can run in its own container, and the code that talks to it needs integration tests.
